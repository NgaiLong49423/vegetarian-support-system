1. MỤC ĐÍCH VÀ PHẠM VI
======================================================================

Tài liệu tổng hợp các lựa chọn công nghệ để thành viên nhóm hiểu công nghệ
nào được dùng, dùng để làm gì, lý do chọn và những đánh đổi cần biết.

Nguồn quyết định: cuộc trò chuyện “Chia câu hỏi chốt công nghệ” và danh sách
xác nhận khi yêu cầu xuất tài liệu ngày 2026-09-11. Các giải thích kỹ thuật
làm rõ lựa chọn; không có nghĩa nhóm đã kiểm thử hoặc triển khai thành công.

“Đã chốt” là baseline hiện tại để nhóm triển khai và thảo luận. Thành viên
có thể đề xuất thay đổi khi yêu cầu hoặc điều kiện phát triển thay đổi;
khi thống nhất thay đổi, cập nhật tài liệu và lịch sử thay đổi tương ứng.

Tài liệu này không chốt thêm kiến trúc tổng thể, cách chia service/module,
database schema, API endpoint hoặc quy trình triển khai. Hai luồng upload
và location được ghi lại vì đã được thống nhất trong cuộc trao đổi.

Version v1.0.0 là phiên bản TÀI LIỆU, không phải phiên bản ứng dụng.
Chỉ Java 21 và JUnit 5 đã được xác định ở mức phiên bản chính như dưới đây.
Không tự suy ra phiên bản cụ thể cho Spring Boot và các dependency khác;
khi thiết lập dự án, cần chọn bộ phiên bản tương thích và ghi trong repo.

Quy ước:
- FE: Frontend — phần giao diện chạy trên trình duyệt.
- BE: Backend — phần xử lý phía máy chủ.
- Đã chốt: lựa chọn hiện tại.
- Future: hướng nâng cấp tương lai, chưa thuộc triển khai hiện tại.
- TBD (To Be Decided): chưa quyết định, để nhóm thảo luận tiếp.

3. FRONTEND
======================================================================

3.1. React — thư viện xây dựng giao diện
- Là gì / vai trò: Thư viện JavaScript để xây dựng UI từ các component
  (thành phần giao diện), ví dụ danh sách công thức, biểu mẫu và trang cá nhân.
- Vì sao chọn: Nhóm có thành viên đã học React, có thể phụ trách FE và hỗ
  trợ những người khác; phù hợp giao diện web gọi REST API của Spring Boot.
- Lợi ích chính: Tái sử dụng component, tổ chức UI theo chức năng, cập nhật
  giao diện theo dữ liệu và tương tác người dùng.
- Đánh đổi / lưu ý: Cần học component, props, state và hooks. React là thư
  viện UI, không phải ngôn ngữ lập trình; việc chọn React chưa quyết định
  thư viện quản lý state toàn ứng dụng hoặc CSS/UI library.

3.2. TypeScript — ngôn ngữ viết frontend
- Là gì / vai trò: JavaScript có hệ thống kiểu dữ liệu tĩnh, giúp mô tả dữ
  liệu component và cấu trúc request/response giữa FE với BE.
- Vì sao chọn: Thành viên FE có nền tảng C# nên tư duy kiểu dữ liệu,
  interface và generic tương đối quen thuộc.
- Lợi ích chính: Phát hiện nhiều lỗi kiểu dữ liệu trước khi chạy, hỗ trợ
  gợi ý code và giúp đổi tên/chỉnh cấu trúc dữ liệu dễ kiểm soát hơn.
- Đánh đổi / lưu ý: Vẫn cần học JavaScript và cơ chế bất đồng bộ. Kiểu dữ
  liệu TypeScript không tự kiểm tra JSON thật nhận từ API tại runtime;
  khai báo interface không bảo đảm dữ liệu server luôn đúng.

3.3. Vite — công cụ phát triển và build frontend
- Là gì / vai trò: Cung cấp môi trường chạy FE khi phát triển và tạo bản
  build giao diện để triển khai.
- Vì sao chọn: Phù hợp React + TypeScript, giúp khởi tạo và phát triển FE
  với lượng cấu hình ban đầu vừa phải.
- Lợi ích chính: Phản hồi nhanh khi sửa giao diện, thống nhất lệnh chạy
  và build trong dự án.
- Đánh đổi / lưu ý: Dev server không phải quyết định hosting production.
  Cần có bước kiểm tra kiểu TypeScript phù hợp; không xem việc chuyển đổi
  mã hoặc build qua Vite là bằng chứng mọi lỗi kiểu đã được kiểm tra.

3.4. npm — quản lý package frontend
- Là gì / vai trò: Quản lý thư viện và chạy các script FE qua package.json.
- Vì sao chọn: Đi cùng hệ sinh thái JavaScript/TypeScript, đáp ứng nhu cầu
  cài thư viện, chạy Vite và build mà không cần thêm package manager khác.
- Lợi ích chính: Chia sẻ danh sách dependency và lockfile để nhóm cài đặt
  nhất quán hơn.
- Đánh đổi / lưu ý: Cần thống nhất môi trường Node.js/npm tương thích với
  bộ dependency đã chọn; phiên bản cụ thể chưa được chốt trong tài liệu.
  Thay đổi package cần cập nhật lockfile và kiểm tra tương thích.

3.5. Axios — HTTP client
- Là gì / vai trò: Thư viện gửi HTTP request từ React tới REST API của BE.
- Vì sao chọn: Thuận tiện gom cấu hình địa chỉ API, header và xử lý lỗi;
  phù hợp nhu cầu giao tiếp FE–BE của dự án.
- Lợi ích chính: Có interceptor để xử lý request/response dùng chung,
  giảm code lặp trong các màn hình gọi API.
- Đánh đổi / lưu ý: Là dependency bổ sung. Cần tránh interceptor gây vòng
  lặp khi xử lý lỗi xác thực; timeout, retry và lưu token cần quyết định
  khi triển khai. Axios không tự quyết định chính sách bảo mật.

4. BACKEND VÀ GIAO TIẾP
======================================================================

4.1. Java 21 — ngôn ngữ và nền tảng backend
- Là gì / vai trò: Java là ngôn ngữ viết logic nghiệp vụ; JDK 21 cung cấp
  công cụ biên dịch và môi trường cần thiết cho phát triển Java.
- Vì sao chọn: Nhóm học chuyên sâu Java, có thể tận dụng kiến thức sẵn có
  và hỗ trợ nhau trong quá trình làm SWP.
- Lợi ích chính: Kiểu dữ liệu rõ ràng, hệ sinh thái thư viện phong phú,
  phù hợp mô hình hóa và kiểm thử nghiệp vụ.
- Đánh đổi / lưu ý: Các thành viên cần thống nhất JDK 21; Spring Boot,
  plugin build và thư viện được chọn phải tương thích với Java 21.

4.2. Spring Boot — framework phát triển backend
- Là gì / vai trò: Hỗ trợ xây ứng dụng Spring, cung cấp cấu hình tự động
  và các starter để phát triển REST API, tích hợp dữ liệu và bảo mật.
- Vì sao chọn: Phù hợp định hướng Java của nhóm và tập hợp nhu cầu backend
  gồm API, nghiệp vụ, database, validation và security.
- Lợi ích chính: Giảm cấu hình ban đầu, tích hợp các thành phần Spring và
  hỗ trợ chạy ứng dụng phục vụ phát triển local.
- Đánh đổi / lưu ý: Cần hiểu dependency injection, cấu hình và vòng đời
  request; cấu hình tự động không thay thế hiểu biết về hệ thống.
  Việc dùng Spring Boot không đồng nghĩa đã chọn monolith hay microservices.

4.3. Maven — build và quản lý dependency backend
- Là gì / vai trò: Quản lý thư viện trong pom.xml, biên dịch Java, chạy
  test và đóng gói ứng dụng.
- Vì sao chọn: Phù hợp hệ sinh thái Java/Spring Boot mà nhóm đang học,
  giúp mọi thành viên dùng chung cách khai báo và build dự án.
- Lợi ích chính: Tự giải quyết dependency bắc cầu, thống nhất quy trình
  build và có thể tái sử dụng các lệnh trong môi trường kiểm thử sau này.
- Đánh đổi / lưu ý: Có thể gặp xung đột dependency hoặc plugin. Build
  thành công không chứng minh kết nối database/cloud và luồng thực tế đúng.

4.4. REST API — giao tiếp frontend và backend
- Là gì / vai trò: Cách thiết kế API quanh tài nguyên và các phương thức
  HTTP để React yêu cầu Spring Boot đọc hoặc thay đổi dữ liệu.
- Vì sao chọn: Đây là hướng giao tiếp FE–BE đã được xác nhận theo môn học.
- Lợi ích chính: Phân chia công việc FE và BE qua hợp đồng API rõ ràng,
  dễ kiểm tra request/response và mô tả bằng OpenAPI.
- Đánh đổi / lưu ý: Cần thống nhất DTO, status code, phân trang và lỗi;
  thay đổi hợp đồng API có thể ảnh hưởng cả hai phía. Chưa chốt endpoint
  hoặc chính sách API versioning trong tài liệu này.

4.5. JSON — định dạng trao đổi dữ liệu
- Là gì / vai trò: Định dạng văn bản có cấu trúc để truyền dữ liệu thông
  thường trong request/response giữa React và Spring Boot.
- Vì sao chọn: Dễ xử lý trong JavaScript/TypeScript và Java, phù hợp REST
  API của dự án.
- Lợi ích chính: Dễ đọc và debug, thể hiện object, array và giá trị cơ bản.
- Đánh đổi / lưu ý: Cần thống nhất ngày giờ, giá trị null và biểu diễn số.
  Upload file có thể dùng multipart/form-data; quyết định JSON không có
  nghĩa mọi request phải nhúng dữ liệu nhị phân vào JSON.

5. DATABASE VÀ PERSISTENCE
======================================================================

5.1. Microsoft SQL Server — database quan hệ chính
- Là gì / vai trò: Lưu dữ liệu nghiệp vụ có cấu trúc và quan hệ như tài
  khoản, công thức, kế hoạch ăn uống và metadata media. Hồ sơ nhà hàng
  không thuộc dữ liệu do hệ thống quản lý.
- Vì sao chọn: Nhóm đã học và sử dụng SQL Server, giúp giảm thời gian học
  hệ quản trị mới và tăng khả năng hỗ trợ nhau.
- Lợi ích chính: Hỗ trợ quan hệ, ràng buộc, transaction và truy vấn SQL;
  phù hợp dữ liệu nghiệp vụ của hệ thống và tích hợp qua JPA/Hibernate.
- Đánh đổi / lưu ý: Cần cấu hình kết nối và môi trường nhất quán. SQL Server
  là nguồn dữ liệu nghiệp vụ chính; ảnh/video thật lưu ở Azure Blob Storage,
  database lưu tham chiếu và metadata. Edition/phiên bản chưa được ấn định.

5.2. Spring Data JPA — lớp hỗ trợ truy cập dữ liệu
- Là gì / vai trò: Cung cấp mô hình repository dựa trên JPA, giảm code
  lặp khi đọc, tạo, cập nhật và xóa dữ liệu.
- Vì sao chọn: Dự án có nhiều thao tác CRUD và quan hệ dữ liệu; tích hợp
  thuận tiện với Spring Boot.
- Lợi ích chính: Giảm phần truy cập dữ liệu phải viết thủ công, hỗ trợ
  truy vấn repository và phân trang.
- Đánh đổi / lưu ý: Truy vấn phức tạp vẫn cần JPQL/SQL phù hợp; cần hiểu
  transaction và SQL thực tế, không chỉ dựa vào tên phương thức repository.

5.3. Hibernate — ORM và implementation của JPA
- Là gì / vai trò: ORM (Object-Relational Mapping) ánh xạ entity Java với
  bảng và quan hệ trong SQL Server; thực hiện hoạt động persistence theo JPA.
- Vì sao chọn: Kết hợp với Spring Data JPA để triển khai truy cập dữ liệu
  trong hệ sinh thái Spring Boot.
- Lợi ích chính: Giảm mapping thủ công giữa object và bản ghi, hỗ trợ
  quản lý entity và quan hệ dữ liệu.
- Đánh đổi / lưu ý: Cần chú ý lazy loading, N+1 query và ranh giới transaction.
  ORM không thay thế thiết kế database, tối ưu SQL hoặc lịch sử migration.
  JPA là đặc tả; Spring Data JPA và Hibernate đảm nhiệm các vai trò khác nhau.

5.4. Flyway — quản lý thay đổi database
- Là gì / vai trò: Quản lý và áp dụng các migration có phiên bản, ví dụ
  V1__create_tables.sql, V2__add_phone.sql, đồng thời ghi lịch sử đã chạy.
- Vì sao chọn: Nhóm đã đồng ý bổ sung để quản lý thay đổi schema theo code
  và giảm lệch cấu trúc database giữa các máy khi phát triển.
- Lợi ích chính: Migration nằm trong Git nên dễ review; từng database biết
  migration nào đã áp dụng và migration nào còn thiếu.
- Đánh đổi / lưu ý: Cần phối hợp thứ tự migration, kiểm tra SQL và chọn bộ
  dependency Flyway hỗ trợ SQL Server phù hợp với Spring Boot đã chọn.
  Không sửa tùy tiện migration đã áp dụng trên môi trường dùng chung.
  Khôi phục dữ liệu cần kế hoạch riêng; Flyway không tự bảo đảm rollback
  mọi thay đổi. Cần tránh để Hibernate tự cập nhật schema cạnh tranh với
  migration; cấu hình cụ thể sẽ thống nhất lúc triển khai.
- Phân biệt: Git/changelog ghi nhận thay đổi mã và quyết định. Flyway theo
  dõi việc áp dụng thay đổi database. IntelliJ/JPA tooling hỗ trợ developer
  tạo hoặc xem mapping/DDL; không thay thế chức năng quản lý migration.

6. AUTHENTICATION VÀ AUTHORIZATION
======================================================================

6.1. Spring Security — framework bảo mật
- Là gì / vai trò: Xử lý authentication (xác thực danh tính) và authorization
  (kiểm tra quyền) cho request tới backend.
- Vì sao chọn: Tích hợp với Spring Boot, đáp ứng nhu cầu đăng nhập và bảo
  vệ API mà không phải tự xây toàn bộ cơ chế bảo mật.
- Lợi ích chính: Tập trung cấu hình bảo vệ endpoint và tích hợp kiểm tra
  token, mật khẩu, vai trò.
- Đánh đổi / lưu ý: Cần cấu hình filter và quyền truy cập đúng; việc thêm
  thư viện không tự bảo vệ tất cả API theo nghiệp vụ mong muốn.

6.2. JWT — token xác thực
- Là gì / vai trò: JSON Web Token, định dạng token chứa các claim; trong
  phương án hiện tại, BE cấp token sau đăng nhập để dùng với API cần xác thực.
- Vì sao chọn: Phù hợp luồng React gọi REST API của Spring Boot đã chọn.
- Lợi ích chính: Request có thể mang token để BE kiểm tra danh tính và
  thông tin quyền đã được cấp, thuận tiện tích hợp FE–BE.
- Đánh đổi / lưu ý: Phải xác minh chữ ký, thời hạn và claim phù hợp.
  JWT có chữ ký không mặc nhiên được mã hóa; không đưa bí mật vào payload.
  Cách lưu token, hết hạn, refresh/logout và thu hồi quyền cần thiết kế tiếp;
  dùng JWT không tự giải quyết các vấn đề này.

6.3. BCrypt — băm mật khẩu
- Là gì / vai trò: Thuật toán băm mật khẩu có salt và chi phí tính toán
  điều chỉnh được, dùng để lưu hash và kiểm tra mật khẩu khi đăng nhập.
- Vì sao chọn: Có thể tích hợp qua cơ chế password encoder của Spring
  Security, đáp ứng nhu cầu không lưu mật khẩu dạng rõ.
- Lợi ích chính: Không cần lưu mật khẩu gốc; salt và chi phí băm giúp tăng
  công sức tấn công dò mật khẩu khi hash bị lộ.
- Đánh đổi / lưu ý: Đây là băm một chiều, không phải mã hóa để giải mã lại.
  Cần chọn chi phí băm và kiểm tra giới hạn đầu vào của implementation;
  không ghi mật khẩu hoặc hash vào log.

6.4. Role-based authorization — phân quyền theo vai trò
- Là gì / vai trò: Gán quyền truy cập theo role của người dùng.
- Vì sao chọn: Dễ hiểu và phù hợp nhu cầu phân biệt các nhóm người dùng
  có trách nhiệm khác nhau trong ứng dụng.
- Lợi ích chính: Quy tắc phân quyền tập trung, dễ giải thích và kiểm thử.
- Đánh đổi / lưu ý: Danh sách role và ma trận quyền chi tiết chưa nằm trong
  quyết định này. BE phải kiểm tra quyền; ẩn nút trên FE là chưa đủ. Quyền
  theo role còn cần kết hợp kiểm tra quyền sở hữu dữ liệu khi nghiệp vụ yêu cầu.

7. MEDIA STORAGE VÀ LOCATION
======================================================================

7.1. Azure Blob Storage — lưu trữ ảnh/video
- Là gì / vai trò: Dịch vụ object storage trên cloud, lưu file ảnh/video;
  SQL Server lưu metadata và tham chiếu tới file.
- Vì sao chọn: Người dùng có tài nguyên cloud/sinh viên và muốn tận dụng
  Azure; phù hợp nhu cầu lưu media trên cloud ngay cả khi ứng dụng chạy local.
- Lợi ích chính: Các máy có thể truy cập kho media chung theo quyền được
  cấp; không phải vận hành máy chủ riêng chỉ để lưu file.
- Đánh đổi / lưu ý: Phụ thuộc mạng và cấu hình quyền truy cập; có thể phát
  sinh chi phí lưu trữ, thao tác và truyền dữ liệu. Credit và điều kiện sử
  dụng phải kiểm tra trên tài khoản; tài liệu không cam kết miễn phí.
  Blob Storage không tự cung cấp đầy đủ pipeline xử lý/chuyển mã video.
  Chọn Azure cho storage không đồng nghĩa đã chọn Azure để deploy ứng dụng.

7.2. Luồng upload hiện tại — ĐÃ CHỐT

  React FE -- gửi file --> Spring Boot BE -- upload --> Azure Blob Storage

- Vai trò: BE nhận request, kiểm tra xác thực/quyền và file, gửi file lên
  Azure; ứng dụng quản lý tham chiếu và metadata trong SQL Server.
- Vì sao chọn: Ưu tiên luồng dễ triển khai, kiểm soát và debug cho giai đoạn
  SWP ban đầu; nhóm chấp nhận việc BE chịu thêm lưu lượng upload.
- Lợi ích chính: Điểm tiếp nhận và kiểm tra upload tập trung ở BE; FE dùng
  một luồng gọi backend quen thuộc cho cả ảnh và video.
- Đánh đổi / lưu ý: Byte dữ liệu đi qua BE nên tiêu thụ băng thông, tài
  nguyên xử lý và có nguy cơ timeout với file lớn/nhiều upload đồng thời.
  Cần kiểm soát kích thước, loại file, xử lý lỗi và tính nhất quán giữa file
  trên Azure với metadata trong database. Chưa có kết quả đo tải thực tế.

7.3. Direct upload bằng SAS URL — FUTURE

  (1) FE xin quyền upload từ BE.
  (2) BE kiểm tra quyền và cấp SAS URL có phạm vi, thời hạn giới hạn.
  (3) FE gửi video trực tiếp tới Azure Blob Storage bằng SAS URL.
  (4) BE xác minh kết quả và quản lý metadata của file.

- Là gì / vai trò: SAS (Shared Access Signature) cho phép cấp quyền giới
  hạn tới tài nguyên Azure Storage; URL này hỗ trợ FE upload trực tiếp.
- Vì sao cân nhắc: Khi video lớn làm luồng qua BE trở nên nặng, có thể giảm
  lưu lượng file đi qua BE. Ảnh nhỏ có thể tiếp tục dùng luồng hiện tại.
- Lợi ích chính: BE tập trung vào cấp quyền và metadata, giảm tải truyền
  file, mở đường cải thiện trải nghiệm upload video lớn.
- Đánh đổi / lưu ý: Phức tạp hơn về CORS, quyền SAS, xác minh file hoàn tất
  và xử lý upload dang dở. Không coi SAS URL là dữ liệu công khai lâu dài.
  Đây là hướng nâng cấp, chưa chốt ngưỡng “video lớn” hoặc cách triển khai.

7.4. Google Maps Platform — tìm nhà hàng chay quanh địa chỉ nhập
- Là gì / vai trò: Member nhập hoặc chọn một địa chỉ; backend dùng Geocoding
  và Places/Nearby Search để lấy nhà hàng chay trong bán kính đã chọn.
- Vì sao chọn: Tránh bắt Admin nhập và duy trì thủ công một danh sách địa
  điểm vốn thay đổi ngoài đời; kết quả thực tế do nhà cung cấp địa điểm trả về.
- Lợi ích chính: Phù hợp nghiệp vụ tìm quanh một địa chỉ cụ thể và không cần
  xin quyền GPS/vị trí hiện tại của thiết bị.
- Đánh đổi / lưu ý: Phụ thuộc quota, giá và chất lượng phân loại của Google.
  Hệ thống không xác minh độc lập rằng mọi món tại địa điểm đều là món chay,
  không quản lý hồ sơ nhà hàng và phải ghi rõ nguồn dữ liệu.

7.5. Địa chỉ và bán kính do Member lựa chọn
- Chỉ Member đã đăng nhập được gọi chức năng; Guest bị chặn trước khi gọi
  dịch vụ ngoài.
- Tâm tìm kiếm đến từ địa chỉ/địa điểm người dùng chủ động nhập hoặc chọn,
  không dùng Browser Geolocation API và không đọc GPS.
- Bán kính MVP gồm 500 m, 1 km, 5 km và 10 km. Cách tính khoảng cách, trường
  kết quả và cách hiển thị được chốt tiếp trong SRS, không suy diễn tại đây.

Luồng location đã chốt:
  Member nhập/chọn địa chỉ và bán kính -> Spring Boot xác thực
  -> Google Geocoding/Places -> trả kết quả có ghi nguồn -> React hiển thị.

Quyết định này thay thế location phase 1 trong v1.0.0 dùng Browser
Geolocation API, restaurant/store trong SQL Server và Spring Boot tự tính
khoảng cách.

9. TESTING, TÀI LIỆU API, VALIDATION VÀ LOGGING
======================================================================

9.1. JUnit 5 — framework kiểm thử Java
- Là gì / vai trò: Viết và chạy test, dùng assertion để đối chiếu kết quả
  thực tế với kỳ vọng; phục vụ kiểm thử logic backend.
- Vì sao chọn: Phù hợp Java/Spring Boot và tận dụng kiến thức kiểm thử từ
  môn Software Testing của nhóm.
- Lợi ích chính: Kiểm tra lặp lại các quy tắc nghiệp vụ và phát hiện lỗi hồi quy.
- Đánh đổi / lưu ý: Cần tình huống và assertion có ý nghĩa, gồm trường hợp
  lỗi/biên. Unit test không thay thế kiểm thử tích hợp hoặc end-to-end.

9.2. Mockito — tạo mock cho kiểm thử
- Là gì / vai trò: Tạo đối tượng giả lập dependency, ví dụ repository hoặc
  client gọi dịch vụ ngoài, để cô lập thành phần đang test.
- Vì sao chọn: Kết hợp với JUnit 5 giúp kiểm tra logic mà không phải luôn
  chạy SQL Server hoặc gọi Azure/Gemini thật.
- Lợi ích chính: Test nhanh, kiểm soát đầu vào/lỗi và giảm phụ thuộc môi trường.
- Đánh đổi / lưu ý: Mock có thể khác hành vi thật. Test dùng mock không chứng
  minh SQL, cấu hình bảo mật hoặc tích hợp dịch vụ ngoài hoạt động đúng.

9.3. JaCoCo — đo code coverage
- Là gì / vai trò: Thu thập thông tin code Java được thực thi khi chạy test,
  tạo báo cáo coverage như dòng lệnh và nhánh.
- Vì sao chọn: Bổ sung bằng chứng định lượng để nhóm nhận biết phần backend
  còn ít được kiểm thử.
- Lợi ích chính: Hỗ trợ rà soát vùng thiếu test và theo dõi độ bao phủ.
- Đánh đổi / lưu ý: Coverage cao không đồng nghĩa assertion đúng hoặc đủ
  nghiệp vụ. Chưa chốt ngưỡng phần trăm bắt buộc hay quality gate.

9.4. OpenAPI — chuẩn mô tả API
- Là gì / vai trò: Đặc tả có cấu trúc về endpoint, tham số, request/response
  và cơ chế bảo mật API.
- Vì sao chọn: FE và BE cần một tài liệu chung để tích hợp, giảm hiểu nhầm
  về dữ liệu và cách gọi API.
- Lợi ích chính: Làm rõ hợp đồng giao tiếp, hỗ trợ công cụ đọc và kiểm tra API.
- Đánh đổi / lưu ý: Phải cập nhật theo hành vi thật, nhất là lỗi và quyền;
  đặc tả không tự chứng minh implementation tuân thủ.

9.5. Swagger UI — giao diện đọc và thử API
- Là gì / vai trò: Hiển thị đặc tả OpenAPI trên web và hỗ trợ gửi request thử.
- Vì sao chọn: Giúp thành viên FE và người kiểm thử khám phá API dễ dàng.
- Lợi ích chính: Xem field và response ngay trên trình duyệt, giảm trao đổi
  thủ công khi tích hợp.
- Đánh đổi / lưu ý: Thử API trên giao diện không thay thế bộ test tự động;
  cần cấu hình quyền truy cập phù hợp với môi trường khi triển khai.

9.6. springdoc-openapi — tích hợp OpenAPI với Spring Boot
- Là gì / vai trò: Thư viện hỗ trợ sinh mô tả OpenAPI từ ứng dụng Spring,
  cung cấp tích hợp Swagger UI qua module tương ứng.
- Vì sao chọn: Gắn tài liệu API với code backend để giảm viết lại thông
  tin cơ bản bằng tay.
- Lợi ích chính: Thuận tiện duy trì tài liệu endpoint và schema dữ liệu.
- Đánh đổi / lưu ý: Cần chọn phiên bản tương thích Spring Boot và bổ sung
  mô tả/ ví dụ khi suy luận tự động chưa thể hiện đủ nghiệp vụ.

9.7. Jakarta Bean Validation — kiểm tra ràng buộc dữ liệu
- Là gì / vai trò: Đặc tả validation dùng các ràng buộc như @NotBlank,
  @Email, @Size trên DTO hoặc đối tượng Java để kiểm tra đầu vào.
- Vì sao chọn: Tích hợp với Spring, giúp khai báo điều kiện dữ liệu nhất
  quán tại backend.
- Lợi ích chính: Giảm kiểm tra lặp lại, phát hiện đầu vào sai sớm và hỗ trợ
  phản hồi lỗi rõ ràng cho FE.
- Đánh đổi / lưu ý: Cần implementation và kích hoạt validation đúng chỗ.
  Không thay thế phân quyền, ràng buộc database hay business rule liên quan
  dữ liệu hiện có, ví dụ email trùng hoặc quyền sửa một bản ghi.

9.8. SLF4J — API/facade logging
- Là gì / vai trò: Giao diện ghi log mà code Java gọi; backend logging phía
  dưới thực hiện việc xuất log.
- Vì sao chọn: Phù hợp hệ sinh thái Spring và tách lời gọi logging khỏi
  implementation cụ thể.
- Lợi ích chính: Cách ghi log thống nhất trong code; dễ phân mức độ log.
- Đánh đổi / lưu ý: SLF4J không tự lưu/xuất log; cần implementation phù hợp
  và tránh cấu hình nhiều provider xung đột.

9.9. Logback — implementation logging
- Là gì / vai trò: Thực hiện ghi log từ SLF4J ra nơi được cấu hình, với
  định dạng, mức log và chính sách lưu phù hợp.
- Vì sao chọn: Kết hợp tự nhiên với SLF4J trong ứng dụng Spring Boot.
- Lợi ích chính: Hỗ trợ debug lỗi API, database và lời gọi dịch vụ bên ngoài.
- Đánh đổi / lưu ý: Log quá nhiều ảnh hưởng hiệu năng và dung lượng. Không
  ghi mật khẩu, token, SAS URL hoặc dữ liệu cá nhân nhạy cảm. Nơi lưu log,
  thời gian giữ và công cụ quan sát tập trung chưa được chốt.
