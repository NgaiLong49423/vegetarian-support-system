# BUG-007: Migration đồng thuận dinh dưỡng lỗi trên SQL Server mới

- Trạng thái: TRACKING
- Khu vực: Backend/Database migration
- Mức độ: High
- Ngày phát hiện: 2026-10-01
- Nhánh/commit: Chưa xác định
- Requirement/Issue/PR: FR-35 / Issue #78

## Triệu chứng

Backend không khởi động được trên SQL Server database mới do Flyway migration `V3__nutrition_profile_consent.sql` thất bại.

## Kỳ vọng

Flyway áp dụng V1, V2, V3 thành công trên database mới và Backend khởi động để phục vụ hồ sơ dinh dưỡng.

## Thực tế

Đã có báo cáo trước đó về Flyway dừng ở V3 với SQL Server error 207: `Invalid column name 'health_data_consent_at'` (log cũng báo `health_data_consent`). Sau đó người dùng chạy SQL thủ công trên `MamXanhDB` và xác nhận hai cột cùng constraint hiện có trong database. Việc kiểm tra trạng thái hiện tại này chưa xác nhận migration chạy thành công trên database sạch.

## Bằng chứng

- Người dùng chạy truy vấn SQL trên `MamXanhDB`; kết quả hiển thị `health_data_consent`, `health_data_consent_at` và `CK_USER_health_data_consent_timestamp`.
- Kết quả trên chỉ xác nhận các đối tượng đang tồn tại trong database được kiểm tra; không chứng minh Flyway áp dụng được V1–V3 trên database rỗng.
- Bản migration hiện tại tạo constraint bằng dynamic SQL. Chưa có bằng chứng xác minh nguyên nhân gốc hoặc chạy lại migration từ đầu trên database sạch.
- Không có bằng chứng nghiệm thu E2E bằng tài khoản đăng nhập thật; không ghi nhận Playwright là đã vượt qua cho chức năng này.

## Tái hiện

Tạo database SQL Server rỗng, khởi động Backend với Flyway bật và áp dụng `V3__nutrition_profile_consent.sql`.

## Môi trường

- Windows 11, Microsoft SQL Server Express 2019, SQL Server JDBC Driver 13.4.0, Spring Boot 4.1.1, Flyway 12.4.0.

## Nguyên nhân gốc

Chưa xác định. Lỗi 207 đã được báo cáo, nhưng kiểm tra schema thủ công sau đó không tái hiện lỗi và chưa có lần chạy migration sạch để xác nhận nguyên nhân.

## Cách xử lý

Migration hiện tại dùng dynamic SQL khi tạo check constraint. Cách xử lý này chưa được xác minh trên database sạch nên lỗi vẫn được theo dõi.

## Kiểm chứng

Ngày 2026-10-01, người dùng xác nhận bằng truy vấn SQL thủ công rằng hai cột đồng thuận và constraint hiện diện trong `MamXanhDB`. Chưa kiểm chứng migration trên database rỗng. Không có xác nhận E2E FE → BE → DB bằng tài khoản thật.
